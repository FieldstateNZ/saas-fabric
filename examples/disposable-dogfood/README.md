# Disposable internal dogfood profile

A throwaway, draft-only run of the SaaS Fabric control plane and operator
console, with a disposable Keycloak for real OIDC sign-in, on one internal
Docker network, published on `127.0.0.1` only. Everything an operator does in it
is lost when it is reset. That is the point.

Source commit: `1f46788ecd5c59af1a4937aae0e51cf59b8f8081`. Nothing here is
production code; nothing here is merged, published or deployed. **No runtime
behaviour has been verified by the author of these files.** Every claim below
about containers starting, Keycloak minting a usable token, the console
signing in, or the firewall gate isolating anything is a design statement
checked against source and unit tests, not an observation. The unit tests
prove the tool *refuses* without evidence; they do not prove the network.

## Where this runs

| | |
|---|---|
| Target daemon | **LucentRoot**, `docker info` ID `47e4864c-619b-4190-8ef5-65d1feceb155`, name `lucentroot`, server `29.5.3` (observed read-only) |
| Socket | `unix:///var/run/docker.sock` only, set explicitly; never a TCP host, never an inherited `DOCKER_HOST`/`DOCKER_CONTEXT` |
| Not | Riley (no local socket). The launcher is meant to be staged onto LucentRoot after separate approval. |

Every Docker-touching command (`build`, `activate`, `status`, `reset`) reads
`docker info` first and refuses any daemon whose ID, name or server version
differ. Docker, git and iptables are invoked by absolute path, with no shell,
and with a constructed environment: fixed `PATH`, `HOME` and `DOCKER_CONFIG`
pointing at a private empty temporary directory (so no operator credential,
context or plugin configuration is ever read), `DOCKER_HOST` as above, and
nothing inherited, including proxies, `COMPOSE_*` and `FABRIC_*`. Compose is
found through the system plugin directory, not the operator's.

## What runs

| Container | Image | Published | Writable paths (tmpfs, `mode=0700`, owned by the container user, `nosuid,nodev`) |
|---|---|---|---|
| `fabric-dogfood-console` | console, built from `apps/control-plane-ui/Dockerfile` target `console` at the pin | `127.0.0.1:18780` | `/tmp` 32 MiB (`noexec`), uid 101 |
| `fabric-dogfood-cp` | control plane, built from `Dockerfile` target `control-plane-api` at the pin | nothing | `/var/lib/fabric/state` 16 MiB, `/tmp` 16 MiB (both `noexec`), uid 65532 |
| `fabric-dogfood-keycloak` | **derived** image: `FROM quay.io/keycloak/keycloak@sha256:9d1f1b2b…de8067` (26.7.2) plus a seed copy and a short generated entrypoint | `127.0.0.1:18781` | `/opt/keycloak/data` 64 MiB, `/opt/keycloak/lib/quarkus` 256 MiB, `/tmp` 64 MiB, uid 1000 (exec allowed: the JVM maps native libraries from `/tmp`) |

All three: `read_only` root, `cap_drop: ALL`, `no-new-privileges`, non-root
user from the image, `pids_limit`, `mem_limit`, `cpus`, capped `json-file`
logs, `pull_policy: never`, no `restart`, image given as an exact local image
ID (never a name or tag, so nothing resolves at run time). No named volumes,
no host paths, no sockets, no host networking, no `entrypoint` override. The
only bind mounts are two generated, read-only config files. Writable paths are
declared under the compose `tmpfs:` key with explicit `size`, `mode`, `uid`
and `gid`; the validator refuses any tmpfs that is world-writable, root-owned,
uncapped, missing, or not in the table above.

**Why Keycloak is derived.** The public image's `start-dev` re-augments into
`/opt/keycloak/lib/quarkus` at boot. Under a read-only root that path must be
a tmpfs, and a tmpfs hides the jars the image ships there, so the earlier
"tmpfs over the shipped directory" mount could not have started. The derived
image is built from a two-file context generated by the tool (`Dockerfile`,
`kc-entrypoint.sh`; nothing else is ever added to a build context, and both
are secret-free by construction and by test): it `COPY --from`s the shipped
`lib/quarkus` to `lib/quarkus.seed` (no `RUN`, no package install), and the
entrypoint refuses to start unless `lib/quarkus` is a writable *empty* mount,
copies the seed in, then `exec`s the stock `kc.sh start-dev`. The base digest
and the derived image's local ID are recorded separately in the lock. That it
starts, and that 256 MiB holds the re-augmented output, is unverified.

The console's own nginx is the operator ingress: the shipped image does not
proxy `/api`, so the generated `console.nginx.conf` replaces its `default.conf`
and adds one `location /api/` that proxies to `cp:8081` on the internal
network. Every `add_header` line from the shipped `nginx.conf` is required to
be present, byte for byte, by the validator.

Control-plane posture (all development adapters the code already names and
warns about at startup): `desired_state = local_directory` on the tmpfs,
`identity_provider = in_memory` (reconciliation converges nothing; the
disposable Keycloak is never written to), `secret_store = in_memory`, no
`[platform_management]`, no `[git_host]`, no `public_base_url`. The operator
posture is `oidc`: issuer `http://127.0.0.1:18781/realms/fabric-dogfood`
(what the browser is sent to and what tokens say), `reachable_at`
`http://keycloak:8080/realms/fabric-dogfood` (where the control plane redeems
codes and reads keys), `redirect_uri` `http://127.0.0.1:18780/`. The validator
re-derives the three endpoints exactly as
`crates/fabric-keycloak/src/operator/endpoints.rs` does. Keycloak's
`KC_HOSTNAME` is pinned to the issuer base so minted `iss` claims match.

`jwks_refresh_seconds = 5` is set explicitly and the validator requires
exactly that value (and that `leeway_seconds` is left at the control plane's
default). This is a startup-ordering setting, not an authentication change:
the control plane reads the realm's signing keys at startup and again every
refresh interval, and in this profile the realm is bootstrapped *after* the
control plane starts, so the production default of 300 would refuse every
bearer for up to five minutes. The keys are still read from the issuer and
every token is still verified. The field already exists in the production
configuration (`operator_config.rs`); the source repository is unchanged.

## Commands

```
python3 examples/disposable-dogfood/dogfood.py                 # default: prepare + check, no Docker
python3 examples/disposable-dogfood/dogfood.py check
python3 examples/disposable-dogfood/dogfood.py prepare --synthetic-pins   # review-only render with fake image IDs
python3 examples/disposable-dogfood/dogfood.py enforcement     # print the host firewall gate and its exact inverse; never applied
python3 examples/disposable-dogfood/dogfood.py build --yes     # git archive of the pin; docker build x2; pull Keycloak by digest; derive it
python3 examples/disposable-dogfood/dogfood.py activate --yes  # fail closed unless daemon + firewall gate verify; compose up; bootstrap
python3 examples/disposable-dogfood/dogfood.py status
python3 examples/disposable-dogfood/dogfood.py reset --yes     # remove only the recorded container/network IDs; delete local state
python3 -m unittest discover -s scripts/tests -v
```

Python 3.11 or newer; standard library only; Linux (`termios`). Docker
Compose v2.24 or newer (long-form `env_file`). The default invocation,
`check` and `enforcement` never call Docker. `build`, `activate` and `reset`
require `--yes`. None of the Docker-touching commands has been run by the
author.

**Staging from a review branch.** `prepare` and `check` refuse unless the
source checkout is at exactly the pinned commit `1f46788…`, because the
console header comparison reads that tree's `nginx.conf`. The commands above
therefore fail when run from the head of the PR branch that carries these
files. Stage them like this instead (nothing below has been executed by the
author):

1. Make a detached checkout of the pin: `git worktree add --detach
   <stage-dir> 1f46788ecd5c59af1a4937aae0e51cf59b8f8081`, and confirm
   `git -C <stage-dir> rev-parse HEAD` prints the full pinned commit.
2. Overlay only the *tracked* files of this directory from the reviewed PR
   ref into that checkout: `git archive <reviewed-ref>
   examples/disposable-dogfood | tar -x -C <stage-dir>`. Tracked files only;
   `.out/` is untracked and must not be copied.
3. Run `prepare` and `check` from `<stage-dir>`. The checkout's HEAD is still
   the pin, so the worktree check passes, and the overlaid launcher is the
   reviewed one. The overlay shows as modified files in that worktree; do
   not commit them there.

**prepare / check.** Reads `profile.toml` (allowlisted keys only), renders
`control-plane.toml`, `console.nginx.conf` and `compose.json` into `.out/`,
validates the *rendered* artefacts, and refuses if anything on disk differs
from what the inputs render to. Refuses a `.env` in either directory, a
worktree not at the pinned commit (the console header comparison reads the
working tree's `nginx.conf`), any `FABRIC_*` variable or `${}` reference, and
a `.out` or `.out/.ephemeral` that is a symlink or a file. Every file is
written with `O_NOFOLLOW`.

**build.** Verifies the daemon, then reads the source through
`git archive 1f46788…` into a private `0700` temporary directory and builds
from *that* context, never from the working tree, so modified or untracked
files (including `.out/`, credentials or anything else) cannot enter an image.
Archive members that are not plain files or directories are refused. If the
working tree's `apps/control-plane-ui/nginx.conf` differs from the pinned one
the build refuses, because the rendered console configuration was derived from
it. Then it pulls the Keycloak digest (the one approved outbound fetch),
checks the pulled image reports that digest, writes the two generated derived
image files into a second private context and builds the derived image. The
lock records the commit, three local image IDs, the base digest and the daemon
identity. Nothing is pushed anywhere.

**activate.** In order, each step a refusal if it fails: a controlling
terminal exists and is a terminal (`/dev/tty` opens read-write and
`isatty`); `check`; lock is real, not synthetic; no credential or
ownership receipt exists; the daemon is the expected one; `iptables -S INPUT`
and `iptables -S DOCKER-USER` are readable and contain the full gate as the
first rules of each chain in order (unreadable, missing, reordered, or any
rule above the gate all refuse); no container with this profile's names or
project label and no network with its name exists (existing resources are
never adopted). Only then, with nothing yet created, it asks the human on
the controlling terminal for a **new** password for the synthetic operator:
read by direct verified-terminal echo-off input (the tool opens `/dev/tty`
itself, requires `isatty`, clears `ECHO` with `termios` on that descriptor,
reads that descriptor only and restores the attributes in `finally`; it does
not use `getpass`, whose fallback can silently read a terminal on stdin),
typed twice, refused if empty, shorter than 16 characters, or mismatched,
and refused (nothing read from anywhere) if `/dev/tty` cannot be opened, is
not a terminal, or its echo cannot be cleared. The
tool never prints, logs or writes that password; it is sent once to
Keycloak when the operator is created and then dropped. A rejected entry
leaves nothing to clean up. Then it creates the bootstrap admin credential
(`.out/.ephemeral/keycloak.env`, exclusive create, `0600`, never through a
symlink), runs `compose up --no-build --pull never`, inspects the three
containers and the network, and accepts them as its own only if name, project
label and locked image ID all match. It writes `.out/ownership.json`
recording their IDs and the SHA-256 of the compose file. If `up` fails or the
resources do not verify, it removes only containers/network that match name,
label and image, deletes the credential, and stops. Bootstrap (realm, public
PKCE-S256 client, `fabric-operator` role, one operator) runs only after the
owned Keycloak container is seen to publish `8080/tcp` on exactly
`127.0.0.1:18781`. Realm bootstrap uses loopback HTTP only (below). On
success the tool prints the operator **username** only; the password is the
one you typed. The CI trial never prompts: it calls `bootstrap_realm`
without a password, which generates one in memory and returns it.

**status.** Loopback readiness evidence: console `/healthz`, `/api/session`
through the proxy, issuer discovery, and the network inspect (internal, IPv6
off, fixed bridge name and subnet, no foreign container).

**reset.** Requires the ownership receipt to validate against the lock and
the compose file on disk (a forged, reshaped or stale receipt, or a tampered
compose, refuses before any Docker call). Verifies the daemon, re-inspects
each recorded container ID and the network ID, and refuses everything if any
no longer matches name, project label and image, or if a foreign container is
attached to the network. Then `docker rm --force <id>` per recorded container
and `docker network rm <id>`. No `compose down`, no `--remove-orphans`, no
`--volumes`, no prune: no volume is ever created, so none is ever removed.
Local state is deleted file by file by exact name (never `rmtree`, never
through a symlink); unexpected files are left in place and reported. Without a
receipt no Docker resource is touched. Images are kept. The firewall rules are
*not* removed by the tool; use the REMOVE lines from `enforcement`.

## Loopback HTTP helper

Only `http://127.0.0.1:<console_port>` and `http://127.0.0.1:<oidc_port>` are
contactable; `localhost`, other addresses, other ports, `https`, URL userinfo
and fragments are refused before a socket opens. The opener is built with
`ProxyHandler({})`, so inherited `http_proxy`/`HTTPS_PROXY`/`no_proxy` are
ignored, and a redirect handler that raises on any 3xx, so a `Location` to a
disallowed port can never be followed and an `Authorization` header can never
be forwarded. The test suite proves this with three real loopback servers: an
allowlisted one answering 302 to a disallowed one, and a proxy trap named in
the environment; the disallowed target and the trap each receive zero
requests. Errors from Keycloak carry the status code only, never a body.

## Network restriction: what is and is not proven

`internal: true` removes the default route and masquerade from the bridge. It
does **not** stop a container reaching the Docker host's own addresses (the
bridge gateway, or a shared Keycloak, OpenBao or Git service published on
`0.0.0.0` on this host), nor anything else routed locally.

The profile fixes the bridge interface name (`fabric-dogfood0`) and subnet
(`10.213.7.0/24`) so a narrow host gate can target exactly this sandbox.
`dogfood.py enforcement` prints it, and `activate` refuses unless it is
already in place:

```
iptables -I INPUT 1 -i fabric-dogfood0 -m conntrack --ctstate RELATED,ESTABLISHED -j ACCEPT
iptables -I INPUT 2 -i fabric-dogfood0 -j DROP
iptables -I DOCKER-USER 1 -i fabric-dogfood0 -m conntrack --ctstate RELATED,ESTABLISHED -j ACCEPT
iptables -I DOCKER-USER 2 -s 10.213.7.0/24 ! -d 10.213.7.0/24 -j DROP
iptables -I DOCKER-USER 3 -i fabric-dogfood0 ! -o fabric-dogfood0 -j DROP
```

The `ESTABLISHED,RELATED` accept comes first in *both* chains, so replies to
connections the host opened to the two published ports pass; the earlier
version of this gate dropped those replies in `DOCKER-USER`. The exact inverse
(`iptables -D …` per rule, reverse order) is printed under REMOVE. There is no
flush, no chain deletion, no policy change, and this tool never applies or
removes any of it: applying is a separately approved host change made by a
person. The preflight reads the chains and requires the five rules to be the
first rules of their chains; it fails closed if `iptables` is missing,
unreadable, or shows anything else above them.

**Runtime negative canaries, required before interactive use.** None of the
above proves isolation. Before anyone signs in, run from a probe attached to
`fabric-dogfood-internal` (the Keycloak image does have a shell; a separate
throwaway probe container is cleaner) and confirm each FAILS: a TCP connect
to the host's bridge gateway address on any listening port; a connect to any
shared service port on the host (Keycloak, OpenBao, Git); a connect to
`1.1.1.1:53` and an HTTP fetch of a public URL. Confirm the console and
Keycloak ports still answer from the host's loopback. Record the output beside
`iptables -S INPUT`, `iptables -S DOCKER-USER` and
`docker network inspect fabric-dogfood-internal`. The tool does not run these
and nothing in this directory claims they would pass.

Registries an operator registers in the console are read at public addresses;
on this network every such read should fail, which is the intended outcome.
Fetching this organisation's public GHCR images is not enabled here. The
Keycloak pull in `build` happens before the network exists.

## Hosted-runner build, and a gated runtime trial (test only, never LucentRoot)

`ci_smoke.py` and `.github/workflows/disposable-dogfood.yml` run on a
GitHub-hosted `ubuntu-24.04` runner that is destroyed when the job ends. The
workflow holds `contents: read`, checks out with `persist-credentials:
false`, uses no repository secret, logs in to no registry, and pushes, tags,
publishes and deploys nothing. Artifacts are the image archives and the
redacted manifest only, retained for one day. **Nothing in this section has
been run by the author of these files; it describes what the script asserts,
not what has been observed.**

### The gate

| Trigger | What runs |
|---|---|
| push to `codex/disposable-dogfood` | **build only**, always |
| `workflow_dispatch`, `runtime_trial` unset or `false` (the default) | build only |
| `workflow_dispatch`, `runtime_trial = true` | build, then the `--runtime` path |

The script's default is build only; `--runtime` is the only way into the
runtime path, and the workflow passes it only from the second step, which is
conditioned on `github.event_name == 'workflow_dispatch'` **and** the boolean
input being true. Playwright is installed only on that path. No `pull_request`
(a fork's PR must not be able to run this with a changed script), no tags, no
`main`, no schedule. GitHub offers `workflow_dispatch` only for a workflow
file that exists on the default branch; until this file is on `main`, the
dispatch form will not list it and the branch push is the only runnable
trigger, which is build only. The runtime path is a separately approved
host/network change on the runner and **has not been executed**. Applying the
gate, starting containers, bootstrapping a realm and probing the network are
not implied by anything here; they need an explicit approval for that
dispatch.

### Build only (the default)

Before anything else the script requires `GITHUB_ACTIONS=true` and refuses
the daemon if its `docker info` ID is `47e4864c-…` **or** its name is
`lucentroot`, in either mode, before any build. Only then does it point
`EXPECTED_DAEMON` at the runner's own daemon, in memory, so every existing
verifier (daemon, lock, ownership, receipt) runs unchanged. That is a test
composition of a host-identity assertion, not an authentication bypass.

1. Builds the control plane and console with `extract_pinned_source` and
   `docker_build` from `git archive 1f46788…`, pulls the Keycloak digest,
   checks the pulled image reports it, and builds the derived image from
   `keycloak_derived_context`. `REPO_ROOT` is repointed at the extracted
   source so the console-header comparison reads the pinned `nginx.conf`.
2. Saves the three images with `docker save` as `<service>-image.tar.gz` in
   the artifact directory.
3. Renders with the genuine image IDs and requires `validate_rendered` and
   `drift_findings` to be empty.
4. Writes `result-manifest.json` and finishes.

It applies no iptables rule, creates no network, starts no container,
bootstraps no realm, creates no credential, opens no browser and makes no
HTTP request. `scripts/tests/test_ci_smoke.py` proves this with scripted
seams: every runtime stage function, `sudo`/`iptables`, the HTTP helper,
realm bootstrap and `time.sleep` are tripwires that fail the test if reached;
the default run must exit 0 having issued only `docker info`, `build`,
`pull <keycloak digest>`, `image inspect` and `save`, with no `.ephemeral`
directory or `keycloak.env` anywhere. The same tests prove LucentRoot is
refused by ID and by name with `GITHUB_ACTIONS=true`, with and without
`--runtime`, after exactly one `docker info`.

### `--runtime` (dispatch with `runtime_trial = true` only; not yet executed)

After the build-only steps, each step an assertion recorded in the manifest:

5. Pulls the pinned `node:22` digest the console Dockerfile names (probe
   helper; runner egress before any trial network exists).
6. Applies the exact five `iptables -I` lines `enforcement` prints, through
   `sudo -n` with a fixed argv, after confirming the gate was absent, and
   requires the existing `preflight_enforcement` to accept them. The
   `finally` deletes exactly those rules with the printed `-D` inverse.
   Nothing is flushed. Only on the runner.
7. `compose up --no-build --pull never`; inspects the three containers and
   the network with `evaluate_owned_container` / `evaluate_owned_network`,
   and additionally requires from the daemon's own inspect: read-only root,
   `cap_drop ALL`, `no-new-privileges`, only the two read-only config
   binds, no socket, the declared tmpfs set, and no `FABRIC_*`, OpenBao,
   Vault or Git-host variable (keys are reported, values never). Writes a
   receipt that `parse_receipt` accepts; `finally` removes those recorded
   IDs with `remove_recorded`.
8. Waits for the master realm on the loopback port, runs `bootstrap_realm`,
   waits for the new realm to serve its key set, then waits one
   `jwks_refresh_seconds` interval (5 s, see above) so the control plane's
   next scheduled key read sees it. **No container is restarted.** The
   first authenticated request in step 11 is retried for a bounded time
   with the real token.
9. Loopback readiness as `status` does: `/healthz`, `/api/session` with
   `evaluate_session_config`, discovery with `evaluate_discovery`; and
   anonymous `GET /api/catalogue` and `/api/operator` must answer 401.
10. Real OIDC: Playwright (`playwright==1.52.0`, installed into a virtualenv
    under `RUNNER_TEMP`, never into the repository) opens the console,
    clicks **Sign in**, asserts the browser landed on the issuer's
    authorization endpoint with `response_type=code`,
    `code_challenge_method=S256` and the console client, fills the Keycloak
    login form with the generated operator, and asserts the console's own
    `POST /api/session` answered 200 and its first `GET /api/catalogue`
    with that token answered 200. The token is captured from that response
    in memory and registered for redaction.
11. As that operator over the proxy: `/api/operator` 200 (retried up to
    30 s with the same token), `createApplication` (`If-None-Match: *` or
    `If-Match`), `saveApplication` of the returned draft with a changed
    description, read back (the control plane's state tmpfs proving
    writable), `releases` empty for every application, `/api/clients`
    empty. No publication, no assignment, no secret, no registry, no
    AcceptingOperator.
12. Connectivity, with a transient read-only unprivileged probe container,
    removed before the network is validated. Positive first: the probe on
    the trial network GETs console `/healthz` and cp `/api/session`. Then
    negatives, each with a positive control: a synthetic listener bound on
    the bridge gateway address (host connects; trial probe must not), a
    synthetic peer container on a separate temporary bridge (probe on that
    bridge connects; trial probe must not), and `1.1.1.1:53` (must not).
    Only the probe's own exit codes 1 (refused/unreachable) and 2 (timed
    out) count as "blocked"; any other failure, including Docker's own 125,
    fails the trial as a broken probe rather than passing as a negative.
    No real shared service is contacted. DNS from the trial network is not
    probed. The negatives would be observed with the gate *and* Docker's
    own internal-network rules in place; the trial does not say which one
    blocked each probe. Afterwards `evaluate_network_inspect` must still
    pass.

### What can and cannot leave the runner

Credentials (bootstrap admin, operator password, access token) exist only in
process memory and in one `0600` file under `RUNNER_TEMP` that `finally`
deletes. Only two kinds of file are written to the artifact directory: the
image archives and `result-manifest.json` (assertions with pass/fail, image
IDs, the runner daemon identity, and on the runtime path the two chain
listings and the network summary), passed through the redaction register
before writing. A failure is reported as the failing assertion's name, or as
an exception class and stage name; never an exception message, never a URL
(an authorization code travels in one), never a Playwright message, never a
container log. Every `docker` and `git` call made by the script discards the
child's stderr and, on failure, keeps only the subcommand word in the error,
so inherited stderr cannot bypass redaction. Cleanup is LIFO over exactly
what the run created: probe and peer container IDs, the peer network ID, the
three containers and network by recorded ID, the five rules, the credential
file, the private work directory. No prune, no flush, no `compose down`. **A
failed cleanup fails the trial**, whatever the assertions said.

Known risks: the Rust release build from an empty cache is the long pole
against the 35-minute job bound; the Keycloak login form selectors
(`#username`, `#password`, `#kc-login`) are those of the stock Keycloak 26
theme; the one-interval wait in step 8 assumes the control plane's refresh
timer runs regardless of whether its startup read found the realm, which the
runtime path would be the first thing to observe.

## Blockers and honest limits

1. **Nothing has been run.** Not the build, not compose, not Keycloak, not a
   sign-in, not the canaries. Runtime verification is outside the current
   no-activation scope. Unverified in particular: the derived Keycloak image
   building and `start-dev` re-augmenting into a 256 MiB tmpfs; Docker

2. **The firewall gate is a precondition the tool checks, not isolation it
   provides.** `activate` refuses without it; it does not apply it, and the
   negative canaries above must pass before interactive use. Reading
   `iptables -S` needs privilege on LucentRoot; if the launcher's user lacks
   it, activation fails closed rather than proceeding.
3. **Compose feature versions.** Long-form `env_file` with `required` needs
   Compose v2.24+; `cpus`, `mem_limit`, `pids_limit` are honoured by `docker
   compose` outside Swarm. If the daemon in use is older, report rather than
   widen.
4. **Keycloak image shell.** The Keycloak image carries bash (its own `kc.sh`
   needs it). The control-plane image is distroless. Neither fact prevents or
   replaces a separate probe container for the canaries.
5. **Draft-only.** With `identity_provider = in_memory` every client reports
   pending forever, no secrets tab works, no registry read succeeds, nothing
   is published, no runtime is assigned. That is the intended scope.
